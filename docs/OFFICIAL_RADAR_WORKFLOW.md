# 官方技术雷达与面试内容更新

## 固定节奏

- 每周一 09:30：读取 `config/official-radar-sources.json`，核对官方来源，只生成技术雷达候选。
- 每月第一个周一 10:00：评审上一个自然月的候选，同时形成课程修改草稿和面试内容修改草稿。
- 正式发布：必须由用户确认后运行“一键提交并发布”；两个定时任务都不得改站点源码、线上数据库、Git 或线上网站。

所有时间使用 `Asia/Shanghai`。

## 每周候选

输出目录：`work/technology-radar/candidates/`，不提交 GitHub。

每条候选必须包含：

1. 来源 ID、权威方、标题、版本或发布日期、官方 URL、发现时间。
2. 与上次记录相比真正发生了什么；没有证据时不得根据标题猜测。
3. 稳定性：正式、稳定、弃用、破坏性、实验、草案或无法确认。
4. 课程影响：涉及的课程、已有内容是否覆盖、建议动作。
5. 面试影响：涉及的能力项、建议新增或更新的问题、追问和评分证据。
6. 风险与待确认项。

去重键使用“来源 ID + 版本/发布日期 + 规范化标题”。同一变化不能在不同周重复成为新候选。

## 每月评审草稿

输出目录：`work/technology-radar/reviews/`，不提交 GitHub。

固定生成三份文件：

- `YYYY-MM-course-draft.md`：课程修改草稿。
- `YYYY-MM-interview-draft.md`：面试内容修改草稿。
- `YYYY-MM-review-summary.md`：候选采纳、合并、观察和拒绝记录。

课程草稿只能把候选归入：修正已有事实、补基础知识卡、更新案例或练习、增加挑战关、新增主关、继续观察、不采纳。新增主关必须有目标、前置知识、小白解释、任务、验收标准和来源。

面试草稿只能提出新增、改写、暂停或归档建议。每道题必须有能力项、题目、追问、优秀回答证据、常见误区、来源和有效期。已有答题证据所引用的题目不能被直接删除或改 ID；需要更新时新增版本并保留旧题归档。

岗位招聘页和技能趋势报告只能影响面试优先级与题目场景，不能直接成为课程技术事实。

## 发布门禁

月度任务完成后只交付草稿路径和摘要。只有用户明确确认本次变更，才允许把草稿转成课程或面试题源码，并运行：

```bash
npm run publish:site -- "课程与面试内容更新说明"
```

发布前仍必须通过构建、测试、敏感信息检查和差异确认。
