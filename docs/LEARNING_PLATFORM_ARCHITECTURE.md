# 测试能力修炼场：学习平台架构

## 1. 平台定位

这是一个帮助学习者持续进步的测试成长平台，不是项目文件浏览器，也不是把本地知识库直接搬上网页的展示站。学习系统与面试成长系统共享同一个平台外壳和能力映射，但保留各自的工作区与职责。

课程以可迁移能力组织。真实项目用于提供案例、任务和证据，但不是课程存在的前提。没有本地项目的 AI 测试、性能测试等模块，仍可以依靠公认基础和实时官方技术建立完整学习路径。

## 2. 三层知识来源

### 公认基础知识

- 优先使用语言、框架和工具官方文档。
- 其次使用正式标准、规范和权威研究机构资料。
- 普通博客和二手文章只能作为发现线索，不能直接成为课程事实。
- 基础知识形成主线课程的稳定骨架。

### 实时技术雷达

- 跟踪官方发布说明、Changelog、PEP、标准修订和权威研究更新。
- 每条雷达信息记录来源、版本、发现时间和最近核对时间。
- 草案、实验性能力和短期热点只进入雷达，不直接进入主线课程。
- 破坏性变化和弃用优先更新已有课程；稳定且可迁移的新能力才考虑新增关卡。

### 本地项目实践

- 当前 Python 框架基础、UI 自动化、API 自动化有本地项目来源。
- Python 来源包括 Skill、校验器、Provider、Runner、生成器和工具脚本。
- UI 自动化来源包括 EWMS/MOM 的 UI 知识库、Locator、Page Object、Playwright 脚本和执行证据。
- API 自动化来源包括 EWMS/MOM 的声明式 YAML、Adapter、Provider、静态门禁、Mock、teardown 和报告。
- 本地路径只用于构建前抽取，不在部署网站中暴露凭证、Token、登录状态或业务敏感数据。

## 3. 模块与来源组合

| 模块 | 公认基础 | 技术雷达 | 本地项目 |
| --- | --- | --- | --- |
| Python 框架基础 | 必须 | 必须 | 已有 |
| UI 自动化 | 必须 | 必须 | 已有 |
| API 自动化 | 必须 | 必须 | 已有 |
| AI 测试 | 必须 | 必须 | 暂无 |
| 性能测试 | 必须 | 必须 | 暂无 |

本地项目增强实践性，但不决定课程是否存在。

## 4. 插件注册模型

平台将来源和课程拆成两种注册对象：

- `SourceAdapter`：声明来源类型、权威方、入口、核对时间和可贡献的知识。
- `LearningModule`：声明课程名称、来源引用、关卡路线和更新规则。

新增模块优先增加注册配置，不修改通用页面；新增来源只需注册 SourceAdapter，再由模块引用。

注册表必须检查：

- 模块 ID 唯一。
- 引用的来源必须存在。
- 关卡 ID 稳定且可迁移。
- 前置依赖不存在循环。
- 来源具备核对时间。

## 5. 统一平台与职责边界

平台采用“一层公共外壳 + 多个独立工作区”结构：

- 公共外壳负责成长总览、全站导航、技术雷达和成长档案。
- 学习中心负责解释知识、安排任务、保存课程进度和验证是否掌握。
- 面试成长负责收集真实回答、形成能力证据、识别薄弱项和生成成长计划。
- `capability-registry.ts` 维护“面试能力项 → 学习课程”的映射，让成长计划可以在同一标签页跳回对应课程。
- 两个系统不共享虚构分数。课程进度来自课程记录，面试能力分只来自真实回答证据。

平台外壳在桌面端是窄侧栏，在移动端是底部导航。业务工作区可以保留自己的二级导航，因此学习页面不会被合并成面试页面，面试页面也不会重复课程内容。

## 6. 页面与路由模型

首页升级为成长总览，学习方向选择移动到独立学习中心。每个模块仍拥有独立地址、独立标题、独立关卡空间和独立知识来源说明：

| 页面 | 地址 | 职责 |
| --- | --- | --- |
| 成长总览 | `/` | 统一呈现学习、面试、雷达三类工作空间及成长闭环 |
| 学习中心 | `/learn` | 展示全部方向，负责课程发现与跳转 |
| 面试成长 | `/interview` | 能力地图、模拟面试、错题本与个人成长计划 |
| 技术雷达 | `/radar` | 展示官方技术源、更新节奏与课程影响 |
| 成长档案 | `/growth` | 聚合本机课程进度、真实回答证据与下一步建议 |
| Python 框架基础 | `/courses/python-framework` | 完整十关、基础知识弹窗、小测与本地进度 |
| UI 自动化 | `/courses/ui-automation` | 独立十关路线与专属来源 |
| API 自动化 | `/courses/api-automation` | 独立十关路线与专属来源 |
| AI 测试 | `/courses/ai-testing` | 独立十关路线与权威知识来源 |
| 性能测试 | `/courses/performance-testing` | 独立十关路线与权威知识来源 |

新增模块时，先在注册表声明模块及来源，再创建自己的课程路由。新增关卡只影响对应课程，不改变平台外壳，也不挤占其他方向的学习空间。

## 7. 新知识如何进入课程

1. 从官方来源或本地项目发现变化。
2. 提取候选知识点并记录证据。
3. 与现有知识图谱对比。
4. 按以下规则处理：

| 变化类型 | 处理方式 |
| --- | --- |
| 缺失的公认基础 | 补入基础关或基础知识弹窗 |
| 稳定、可迁移的新能力 | 增加进阶主关卡 |
| 已有能力的新难度 | 增加挑战关或支线任务 |
| 已有能力的新项目示例 | 更新案例和练习 |
| 尚未稳定的新技术 | 保留在技术雷达 |
| 纯业务字段或页面变化 | 不进入课程 |

新增主关卡必须具有：明确目标、前置知识、小白解释、实践任务和客观验证。

### 更新节奏

- 每周新增：读取官方版本、Changelog、标准与权威研究，建立可追溯候选项。
- 每月更新：评审候选项应新增主关、补知识卡、更新练习还是继续观察。
- 项目触发：本地项目变化先做知识差异分析，只有出现新的可迁移能力或必要前置知识才新增主关。

技术雷达提供“发现”，课程评审负责“发布”，两者不能合并成无人审核的自动加关流程。

## 8. 学习进度与版本

- 进度使用 `moduleId.levelId` 保存，不依赖关卡顺序。
- 新增关卡不清空旧进度。
- 文案和案例更新不影响已通关状态。
- 验收标准发生实质变化时标记“建议复习”，不直接删除历史。
- 删除的关卡进入历史归档。
- 页面展示已掌握能力、待补前置知识、新增内容和需要复习的知识，而不只展示完成百分比。

## 9. 安全与内容边界

- 部署内容不得包含账号、密码、Token、Cookie、storage state、数据库连接或真实业务数据。
- 项目材料先经过白名单抽取和脱敏，再生成教学快照。
- 官方链接在页面展示最后核对日期。
- 技术雷达的自动发现不等于自动发布；进入课程前必须通过课程价值判断。
