# 真实需求与代码库驱动的课程改造

## 总体决策

整个学习中心都采用同一条主线，而不只改工程型关卡：**真实需求 → 实际测试项目 → 课程推进进度**。

- 概念课从这个项目中选取真实结构，解释它为什么存在、处于哪一层、和上下游有什么关系；不为了形式强制安排动手练。
- 实践课修改同一个项目中的关键 TODO，通过测试、日志、静态检查或代码差异验证结果。
- 工程型关卡不再把网页中的单个代码片段当作最终实践环境，而是提供经过脱敏、固定版本、可以独立运行的代码库。

网页负责解释需求和组织学习步骤；VS Code 负责编辑、补全、断点调试和测试；本地课程连接器只执行登记过的项目与命令，并把退出码、测试日志和耗时返回网页作为执行证据。AI 批改只能补充代码审阅和解释，不能替代真实运行结果。

## 当前状态：入口已建立，真实项目待绑定

目前还没有收到用户的实际需求与实际代码库，因此平台不会虚构一个“真实项目”，也不会把工单教学示例冒充业务项目。

学习中心首页、各门课程和各关卡都提供“真实需求项目待绑定”入口，统一指向项目接入说明。明天获得真实需求和代码后，再建立需求与课程的映射，重排课程内容和进度。

## 已完成的技术样板（不等于真实业务项目）

`python-agent-level-08` 已用于验证网页、VS Code 和测试证据链路是否可行：

- 项目使用 `src/`、`tests/`、`data/`、`.vscode/` 和 `pyproject.toml` 组成可运行仓库；
- 课程只要求学员补 `settings.py` 的关键 TODO；
- HTTP 交互由 `httpx.MockTransport` 验证，不访问真实网络；
- 网页提供“在 VS Code 中打开”和“运行本关验证”；
- 本地连接器只接受登记的 `exerciseId`，不能接收任意文件路径或 Shell 命令；
- 已存在的学员工作区不会被课程更新覆盖；
- 验证结果返回命令、退出码、耗时、stdout 和 stderr。

## 明天按具体需求重新安排整个学习中心时

每个候选需求先填写以下清单，再决定拆成哪些关卡：

1. **需求背景**：谁在什么场景下需要什么能力，为什么需要。
2. **真实输入与输出**：字段、示例、数据来源和失败响应必须明确。
3. **边界**：允许访问哪些文件、接口、数据库或工具；禁止什么副作用。
4. **验收标准**：可由测试、静态检查、日志或人工审阅证伪，避免“理解了”一类不可验证表述。
5. **起步仓库**：提供目录、类型、函数签名、测试入口和固定样例，只留下与本节目标直接相关的 TODO。
6. **执行证据**：至少包含固定命令、退出码和测试日志；必要时再增加覆盖率、类型检查和代码差异。
7. **故障练习**：除了成功实现，还应包含复现失败、定位根因、修改和回归测试。
8. **版本来源**：记录原始仓库、commit、脱敏方法和课程快照版本，避免主分支变化破坏题目。

## 后续里程碑

### 第一阶段：绑定真实需求与项目

- 固定允许教学使用的仓库、分支或 commit，并完成脱敏审查；
- 把需求中的角色、字段、流程、异常和验收标准映射到实际代码；
- 为每门课程标注它解决项目中的什么问题，以及产出会落到哪些文件；
- 概念关只要求能解释项目结构和决策，实践关才要求修改与运行。

### 第二阶段：真实运行闭环

- 将可运行项目扩展到所有工程型关卡；
- 为每关登记固定测试、格式检查和类型检查命令；
- 把运行证据纳入通关状态，文字助教不得伪造“已经运行”；
- 增加显式“重置项目”流程，重置前展示代码差异并要求确认。

### 第三阶段：真实代码库导入

- 从指定仓库与固定 commit 创建只包含必要文件的课程快照；
- 自动扫描密钥、账号、客户数据和内部地址；
- 保存来源映射，但面向学员时只展示经过许可和脱敏的内容；
- 使用 Git worktree 或独立练习目录隔离每次修改。

### 第四阶段：L3/L4 训练

- L3：从真实缺陷开始，要求复现、日志、根因、补丁和回归测试；
- L4：增加 ADR、接口契约、迁移与回滚、CI 门禁和评审记录；
- 学员提交的不只是最终代码，还包括为什么采用、如何证伪、何时拒绝 AI 建议。

## 安全边界

- 远程网页不能直接读取任意本地文件或执行任意命令；
- 本地连接器只监听 `127.0.0.1`，只接受允许的站点来源；
- 项目路径和运行命令由代码注册表决定，不接受网页传入路径或参数；
- `.env`、虚拟环境、认证信息和真实业务数据不得上传；
- 将来接入业务仓库时默认只读原仓库，在独立 worktree 或练习副本中修改。
